# 日本の集合住宅(アパート・マンション)プロシージャル生成ジェネレータ — 調査・実装計画レポート

対象コードベース: `house-gen` リポジトリ / 新設 `src/apartment/`
前提: `src/gen`(戸建)・`src/store`(ロードサイド店)と同じ「`gen/`(Three非依存・移植可能な純ロジック)+ `viewer/` + `*-main.ts`」構造、`shared/{vec,rng,poly,geom2d}` 共有、`rand01` 決定論、整数ベイ格子、単一 interface + `Partial` プリセットを厳守する。

数値凡例: **[確定]** = 一次資料で確認済み / **[要確認]** = 自治体・型式で値が振れる、または実装前に一次条例確認が必要 / **[補正]** = 元調査値を検証で修正した値。

---

## 1. 概要と設計方針

### 1.1 このジェネレータが戸建・店舗と決定的に違う点

戸建(`src/gen`)は archetype 合成(core + wings → rect/L/T/U)、店舗(`src/store`)は単一箱 + 前面駐車。集合住宅の骨格はそのどちらでもなく、

> **「可変幅の住戸ユニットを整数ベイ上に線形タイリング(端から詰め・端数吸収)」+「アクセス型に応じた循環コア(階段室/EV)の差し込み」+「基準階を全階へ垂直スタック」**

で決まる。したがって footprint 段階の**前に** `tileUnits`(住戸ミックスのビンパッキング)と `placeCores`(コア配置)の2段を新設する。これが本ジェネレータの主役であり、他は既存資産の流用で足りる。

### 1.2 設計方針(3原則)

1. **アクセス型(`accessType`)が最上位パラメータ** — 住棟奥行き・どの長辺がバルコニー面/廊下面か・コア数・廊下スラブの生成側を連鎖的に決定する。戸建の archetype に相当する骨格スイッチ。
2. **`structure`(構造)がゲート値** — 木造/壁式RC/ラーメンRC/S造が、最大階数・スパン・階高・屋根形式(木造=勾配)・耐火グレードの有効域をクランプする。プリセット外の手動組合せ(木造20階等)はフォールバックで潰す。
3. **既存規約の完全踏襲** — 座標系(XY+Z上、`toThree(x,y,z)=(x,z,-y)`、lot-local `u`=街路平行/`v`=道路からの奥行)、決定論(`rand01`/`Rng`/`weightedPick` のみ、`Math.random()` 禁止)、単一 tunable 源(`AptConfig`)、整数ベイ格子→`rasterizeRects`→`traceBoundary`→tier。

### 1.3 生成パイプライン(全体像)

```
AptLot ─► planAptSite ─► AptSitePlan{pad, parking, bike, refuse, approach, zones, props, fences}
                              │
          placeCores(cfg,pad) ─► CorePlacement[] + CorridorSpec   ← 新規段
                              │
          tileUnits(cfg,pad,cores) ─► Unit[](基準階)              ← 新規段・主役
                              │
   generateAptFootprint ─► {ring, tiers, masses}  (住戸+コア+廊下 → ベイ格子合成)
                              ├─► generateAptFacade ─► {panels, balconies}
                              └─► buildAptRoofs ─► RoofMass[] + 塔屋PH + Canopy
```

## 2. 住棟形式・アクセス型の分類と生成戦略(戸建 archetype との対比)

### 2.1 2軸の骨格モデル

集合住宅の「アーキタイプ」は独立2軸の積で表現する。`config` に enum として持つ。

- **軸A: アクセス型 `accessType`** — コアと共用通路の型。住戸の並び・コア数・採光条件・住棟奥行きを決める最上位。
- **軸B: 住棟形状 `massForm` / `planShape`** — 板状(slab, I/L/U)/塔状(point-tower)/接地型(low-rise)。フットプリント縦横比と階数レンジを決める。

### 2.2 アクセス型の分類・連なりの単位・生成規則

| アクセス型 (`accessType`) | 連なりの単位 | コア | 住棟奥行き | バルコニー/廊下面 | 規模帯 |
|---|---|---|---|---|---|
| **階段室型** `stair-access` | 1階段室あたり各階**2戸**(端部3戸)。2戸×n層を1ユニットとして反復 | 階段のみ(EVは4階以上で階段ごと) | 住戸奥行のみ(**廊下なし**) | 各戸2面(端部3面)開放。廊下スラブ生成なし | 3〜5階、公団団地・低層 |
| **片廊下型** `single-corridor` | 外部開放廊下に住戸を一列連続。棟長=戸数×スパン | 端部/中間に階段+EVを集約 | 住戸奥行 + 外廊下幅 ≈ **12〜15m** | 北=廊下(玄関/小窓)、南=バルコニー | 中〜高層、最頻出 |
| **中廊下型** `double-corridor` | 中廊下両側に背中合わせ、1スパン**2戸** | 端部/中間コア | 住戸2列 + 中廊下 ≈ **24〜27m** | 妻側のみ窓、両面バルコニー | 中〜高層、都心・ワンルーム投資 |
| **コア型** `core-tower` | 中央コアを住戸が**周回**(線形バー前提が崩れる) | 中央1コア(EV複数) | 正方形寄り、縦横比 **1:1〜1:1.5** | 各戸複数方向 | 塔状・超高層 |

派生: スターハウス(Y字・**1フロア3住戸**・中心に階段室コア。公団の中層スターハウス最終竣工は名和団地1964年 **[確定/補正]**「公団の中層」と限定するのが正確)は専用の Y字3分岐マスジェネレータとして扱う(M2以降のオプション)。接地型(テラス/タウン/メゾネット)は低層プリセットで対応。

### 2.3 戸建 archetype との対比(実装上の差別化点)

| | 戸建 (`src/gen`) | 店舗 (`src/store`) | 集合住宅 (`src/apartment`) |
|---|---|---|---|
| 建物本体の構成 | core + wings 合成 | 単一箱 | **住戸ユニットの線形タイリング + コア差し込み** |
| 反復単位 | facade の bay | frontage の bay | **住戸(可変ベイ)を u方向反復 × 階を Z方向スタック** |
| 主難所 | wing 配置 | 駐車到達性 | **可変幅住戸のビンパッキング + コア到達性 + 附置義務充足** |

## 3. 構造・階高・スパン

### 3.1 規模帯 → 構造の一次分岐(`structure` ゲート)

| 構造 `structure` | 典型階数 | ベイ(u方向) | 立面表現 | 屋根 |
|---|---|---|---|---|
| `wood`(木造在来/2×4) | 2階(木3共で3階) | 910尺グリッド、無柱スパン上限≈3640mm | 軒・庇、開口自由 | 勾配(gable/hip) |
| `steel`(重量鉄骨ラーメン) | 3階〜中層 | 大スパン、ALC外装+パネル目地 | 柱スパン、耐火被覆 | 陸屋根/勾配 |
| `rc-wall`(壁式RC / WRC) | **≤5階** | 耐力壁で細分、大スパン不可 | **柱梁が出ずフラット面**+耐力壁間の整列開口 | 陸屋根+パラペット |
| `rc-frame`(ラーメンRC) | 5〜15階 | 経済スパン6〜8m | **柱型(スパン1/10)・梁型(せい600〜800)下がり天井**を立面に出す | 陸屋根+パラペット |
| (SRC/CFT) | 超高層 | より細い柱で大スパン | ラーメン類似 | 陸屋根 |

**立面の最重要分岐**: `structure==='rc-wall' && floors<=5` → 柱梁なしフラット面 + 厚い耐力壁 + 整列開口。それ以外 → 柱型・梁型を立面と室内に出す。

### 3.3 耐火グレード決定(規模 → 構造の強制分岐)

`防火地域フラグ × 階数 × 延べ面積` から耐火/準耐火/非耐火を算出し、木造可否と開口の防火設備(防火窓)・軒裏/外壁防火仕様を切替。

- **法27条 [要確認/補正]**: 共同住宅は法別表第一(2)項の特殊建築物。2019年改正で **階数3かつ延べ面積200㎡未満**、かつ**令110条の5の警報設備(自動火災報知設備等)設置**を条件に耐火/準耐火義務が適用除外。※「3階以下」ではなく「階数3」、警報設備が必須。4階以上または200㎡以上は除外されない。
- **木3共 [確定/補正]**: 1時間準耐火 + 各住戸に避難上有効なバルコニー + 周囲幅員3m通路 +(準防火地域では)3階住戸開口部を防火設備 → 準耐火建築物で可。**防火地域には建設不可**(元調査の「防火/準防火地域」括弧書きは不正確)。準防火地域では延べ1,500㎡以下等の規模上限あり。
- **防火地域 [確定/補正]**: 階数3以上(**地階含む**)または延べ100㎡超 → **耐火建築物 または 延焼防止建築物**が必須(H30改正・法61条代替ルート)。

## 4. 住戸プラン・モジュール・住戸ミックス

### 4.1 モジュール(寸法グリッド)

**[補正]** 尺モジュール=**910mm(=半間=3尺)**、**455mm=四半間(1尺5寸)**(元調査「半間455」は誤り、455は四半間)。メーターモジュール=**1000mm**、両者の差は**9cm**[確定]。

→ 生成規則: `gridModule = 0.9`(基本)/`1.0`(メーターモジュール切替)。住戸間口・壁長はこの整数倍にスナップ(house-gen の `panelW` 整数倍ルールを踏襲)。RC分譲は「構造柱スパン(5.4〜7.2m)で割り、内側を910/1000で刻む」二層構造。

### 4.2 住戸タイプ → 間口ベイ・面積レンジ(面積→部屋数の単調写像)

| タイプ | 専有面積 | 間口 | 奥行 | `unitBays`(×0.9m) | 用途 |
|---|---|---|---|---|---|
| 1R | 18〜30㎡ | 3.0m固定 | 6.0〜7.5m可変 | 2 | 単身・投資 |
| 1K | 20〜30㎡ | 3.0〜3.6m | 6〜8m | 2 | 単身 |
| 1LDK | 30〜50㎡ | 5.4〜6.4m | — | 3 | DINKS |
| 2LDK | 55〜70㎡ | 6m前後 | 11〜13m | 4 | カップル/コンパクト分譲 |
| 3LDK | 60〜75㎡(代表70) | **約6.0m**(田の字) | 11〜13m | 5 | 分譲ファミリー最頻 |
| 4LDK | 75〜90㎡超 | ワイド7〜9m | 短縮 | 6 | 減少傾向 |

- **賃貸ワンルームの原型 [確定]**: 「サブロク=間口3.0m×奥行6.0m=18㎡」。**間口3m固定・奥行延伸**で25〜30㎡へ世代進化。生成規則: `奥行 = 面積/間口` を6.0〜7.5mにクランプ。
- **ワンルーム条例(最低専有面積) [確定/要確認]**: 標準**25㎡**下限。商業地域は総戸数1/2未満に限り20㎡(緩和区のみ)。渋谷区**28㎡**、葛飾区30㎡。※新宿区は25㎡(28㎡は渋谷が正)。区ごとに条例が異なるため実装値は**要一次条例確認**。

### 4.3 バルコニー奥行・開口(重要補正)

**[refuted→補正]** バルコニー奥行の**標準は0.9〜1.5m**(単身・古い物件は910mm≈0.91m、ファミリー築浅で1.0〜1.5m)。1.5〜2.0m=広め、2.0m超=上限クラス。元調査の「標準1.8/2.0m」は誇張。→ `balconyDepth` デフォルトは **1.5m** 程度が妥当(元案1.8は「広め」寄り)。避難上有効なバルコニーは有効奥行0.75m以上。
掃き出し窓の開口高さ**約2.0m(ハイサッシ2.2m)**は妥当[確定]。

### 4.4 住戸内部ゾーニングと立面の非対称ルール

住戸矩形を **廊下側帯**(v小=玄関+水回りUB/洗面/トイレ+MB/PS+廊下側居室)と **バルコニー側帯**(v大=LDK+主寝室、掃き出し窓)に2分割。

**[補正]** MB(メーターボックス)は**各住戸ごとに個別に玄関脇へ分散配置**(元調査「集約」は誤解を招く)。MB空間・PS・本管〜メーターまでの配管は共用部だが、MB内の給湯器やメーター以降の配管は専有部。

→ 立面規則: 廊下側 = `[玄関ドア(W800〜900×H2000) + MB扉 + PS + 小窓(面格子)]` の反復、バルコニー側 = `[掃き出し窓 + 手摺H1100]` の反復、妻側 = 無開口/小窓1。両端に妻住戸(間口拡大 + 側面追加開口可)。

### 4.5 住戸ミックス(`unitMix`)と反復度

| 物件種別 | ミックス比(実務代表値) | 間口反復度 |
|---|---|---|
| 賃貸単身 | 1R/1K = 90〜100%(単一タイプ反復) | 高反復(間口2.7〜3.6m) |
| 賃貸ファミリー | 1LDK 40% / 2LDK 40% / 3LDK 20% | 中 |
| 分譲ファミリー | 3LDK 50〜70% / 2LDK 20〜30% / 4LDK・1LDK 端数 | 中〜高多様度 |

→ `unitMix: Record<type, weight>` を `weightedPick` で1フロア分抽選し、バー長へ justify。`archetypeWeights` と同形式。

## 5. 法規・ボリューム制限・避難(建築可能エンベロープの決定ロジック)

### 5.1 用途地域別ボリューム上限(`HousePad` の総床上限)

| 用途地域 | 建蔽率 | 容積率 | 絶対高さ | 共同住宅 |
|---|---|---|---|---|
| 一種/二種低層住専・田園住居 | 30〜60% | 50〜200% | **10m or 12m** | 可(実質2〜3階) |
| 一種/二種中高層住専 | 30〜60% | 100〜500% | なし | 可(中高層主力) |
| 一種/二種住居・準住居 | 50〜80% | 100〜500% | なし | 可 |
| 近隣商業 / 商業 | 60〜80% | 100〜1300% | なし | 可(高層/タワー) |
| 準工業/工業 | 50〜80% | 100〜500% | なし | 可 |
| 工業専用 | — | — | — | **不可** |

前面道路幅による容積低減(住居系 ×0.4 / その他 ×0.6)で指定値より下がる場合が支配的。

### 5.2 容積率不算入(延床の割増) [確定]

| 部位 | 不算入 |
|---|---|
| 共用廊下・共用階段(共同住宅・老人ホーム等) | **全部不算入(上限なし)**(法52条6項) |
| EV昇降路 | **全部不算入**(H26改正、対象はEVのみ) |
| 住宅用途の地階 | 住宅床面積の1/3限度 |
| 自動車車庫・駐輪場 | 延べ面積の1/5限度 |

→ **総床 ≈ 容積対象床 × 1.1〜1.25**。`planAptSite` で `容積率 × 不算入補正(×1.1〜1.25)` を総延床上限とし、`住棟フットプリント面積 × 階数` を制約。

### 5.3 高さ包絡マスク(斜線 + 絶対高さ + 日影 + 天空率)

建物高さ = 以下の最小値。敷地の道路配置・隣地・真北から傾斜面を生成し、その内側にマスを収める。上層階を段状(北側・道路側)にセットバックする(`upperSetback`)。

| 制約 | 値 |
|---|---|
| 絶対高さ(低層系) | 10m または 12m [確定] |
| 道路斜線 勾配 | 住居系1.25 / 商業・工業1.5(適用距離20〜50m) |
| 隣地斜線 | 住居系 20m+1.25 / 商業・工業 31m+2.5 |
| 北側斜線 | 一低/二低 5m+1.25 / 一中高/二中高 10m+1.25 |
| 日影規制 測定面高さ | **[要確認/補正]** 低層系 **1.5m** / その他 **4mまたは6.5m**(自治体条例で指定。元調査「4m一択」は不完全) |
| 天空率 | 3斜線を天空面積比で適用除外可(斜線超過モードのフラグ) |

### 5.4 避難規定(コア数・住戸並びの決定)

| 規定 | 値 |
|---|---|
| 直通階段までの歩行距離(令120条) | 準耐火/耐火/不燃 **50m** / その他30m(メゾネット40m) [確定] |
| 2方向避難(令121条) | その階の居室床面積合計 **100㎡超**(準耐火/耐火 **200㎡超**)、または**6階以上に居室**で2直必須 [確定/補正] ※100/200㎡は避難上有効なバルコニー等がない場合。6階以上は全用途 |
| 重複区間 | 歩行距離の1/2以下(準耐火25m) |
| 共用廊下 有効幅(令119条) | **[確定]** 両側居室(中廊下)**1.6m以上** / その他(片廊下)**1.2m以上**(住戸床面積合計>100㎡/階)。※表は「両側居室/その他」の2区分で、「片側のみ居室」限定文言ではない |
| 共用階段(令23条) | **[refuted→補正]** 共同住宅共用階段は住宅緩和(蹴上23/踏面15)の**対象外**。直上階居室床面積>200㎡の地上階=**幅1.2m・蹴上≤20cm・踏面≥24cm**(区分3)、それ未満の小規模=**幅75cm・蹴上≤22cm・踏面≥21cm**(区分4)。踊場は令24条で区分3/4は高さ4m以内ごと |
| バルコニー手摺/屋上パラペット | **[確定/補正]** 1.1m以上(令126条、令117条該当建物=特殊建築物/階数3以上等)。足がかり(腰壁300〜650mm)上端から1.1m。共用廊下手摺は自治体条例。隙間内法110mm以下 |
| 避難上有効なバルコニー | 奥行≥0.75m・面積≥2㎡、出入口幅≥75cm×高さ≥180cm(2直緩和の要件) |

→ **コア数決定**: 各階居室床面積>100㎡ または6階以上 → 2コア必須(`ceil(住戸数/stairSpacingUnits)` は階段室型)。歩行距離50m・重複区間25mで階段を住棟両端/分散配置 → 片廊下型の住棟長さ上限 ≈ 100m。

### 5.5 EV設置・採光

- **EV**: 3階以下=任意、4〜9階=1基必須(実務標準)、**高さ31m超(≈10〜11階)=非常用EV追加**(令129条の13の3)。`elevator: 'auto'` は `floors>=4` で真。
- **採光(法28条)**: 居室の有効採光 = 床面積の**1/7以上**(有効採光=開口面積×採光補正係数、住居系 = D/H×6−1.4、上限3)。外気非接続の居室を禁止する制約。ワンルーム25㎡で約3.6㎡、ファミリー居室12㎡で約1.7㎡の開口が目安。中廊下型は各住戸の外気接面確保 → 住棟奥行き・光庭の要否を規定。
- **塔屋(PH)不算入 [refuted→補正/重要]**: 令2条の2規定に分離。
  - **高さ不算入(令2条1項6号ロ)**: 水平投影面積合計が建築面積の**1/8以内**で、原則**12m**(低層住専の高さ制限・日影では**5m**)を上限に高さ不算入。ただし北側斜線・高度地区・避雷設備では緩和されず算入。
  - **階数不算入(令2条1項8号)**: 1/8以下なら階数不算入(**高さ上限なし・面積要件のみ**)。

## 7. 共用部・立面ディテール・屋上

### 7.1 立面の基本グリッド(店舗 `panelW × panelH` パネルモデルにそのまま乗る)

- `panelW` = 住戸スパン: ワンルーム3.0〜3.6m / ファミリー6.4〜7.2m
- `panelH` = 階高: 2.8〜3.0m(木造2.9)
- 住戸ユニット(1スパン)を u方向に n戸 反復 × 階(Z)方向に floors 反復 → 全階が垂直整列(store の split grammar + 位置ハッシュRNG と同原則)。

### 7.2 共用部ディテール

- **片廊下(外部開放)**: 有効1.2m以上(バリアフリー望ましい1.5)。廊下側ファサードに玄関ドア+MB扉+PS+小窓が住戸スパンごとに反復。手摺H1100以上。開放廊下は居室床より下げ外側へ水勾配。
- **中廊下(内部)**: 有効1.6m以上(望ましい1.9)。両側住戸ドア、窓なし、玄関はアルコーブ配置。
- **共用階段**: 折返し階段室は平面 幅2.5〜3.0 × 奥行4.5〜6.0m のボリューム。妻側端部コアが多い。
- **塔屋PH**: EV棟 屋上スラブ+3.5〜4.5m、階段室PH +2.5〜3.5m。建築面積1/8以内(§5.5補正参照)。

### 7.3 バルコニー(反バルコニー面の反復)

奥行**1.0〜1.5m**標準(§4.3補正)。手摺H1100以上(アルミ格子/ガラス/コンクリ立上り+笠木)。隣戸隔て板H1800(中桟1200)。掃き出し窓(2枚引違W1650〜/4枚引違〜W3470、H1800〜2400、ハイサッシ2100超)が住戸幅いっぱいに反復。物干金物・給湯器・室外機を付帯。

### 7.4 立面グラマー(face role)

store の wall role(street/garden/side)を拡張し、`WallFace.role: 'balcony' | 'corridor' | 'gable' | 'entrance'`。

| face role | 開口 |
|---|---|
| balcony(南/道路面) | 各住戸に掃き出し窓 + 手摺H1100 の反復 |
| corridor(北/廊下面) | 玄関扉 + MB扉 + PS + 小窓の反復 |
| gable(妻側=戸境壁側) | 無開口 or 各階小窓1(耐力壁・タイル大面) |
| entrance(1F) | ピロティ/エントランス(ガラス+庇+風除室)/店舗併用(signband流用) |

### 7.5 屋上

陸屋根 + パラペット(防水立上り150mm以上、天端笠木、水勾配1/50〜1/100でルーフドレンへ)。塔屋PHをコア位置に生成。屋上props: 高架水槽・キュービクル・室外機群・避雷針(H20m超)・ハト小屋・タラップ。木造プリセットは勾配屋根(3〜5寸≈17〜27°、軒の出600〜900mm)。

### 7.6 外壁マテリアル(`wallStyle` を seed 解決)

| スタイル | 特徴 | グリッド線 |
|---|---|---|
| tile(吹付タイル/45二丁掛) | **[補正]** 45二丁掛=95×45×7mm(目地共100×50)、シートは公称300角(実測285×292等)、裏面は**ネット貼り**(「紙貼り」は誤り)。目地は定ピッチで実質固定 | 縦横目地+伸縮調整目地 |

| siding(木造) | サイディング | 継目 |
| twotone | 基壇/基準階/妻面でトーン差 | 見切り・水切りの横ライン |

### 8.3 パイプライン段階

1. **`planAptSite(lot,cfg) → AptSitePlan`** — 住棟の敷地内配置(南面/道路の2軸、store の buildingDepth×buildingSide を `southFacing` 対応に改変)、附置義務駐車(`fillParkingRegion`/`mergeParking` 無改変再利用)+駐輪+ゴミ+アプローチ+外構+外周フェンス。pad(整数ベイクランプ)出力。
2. **`placeCores(cfg,pad) → CorePlacement[] + CorridorSpec`** 【新規】 — accessType からコア種別・個数・ベイ位置・廊下生成側/幅を決定。全住戸到達性を保証。`Rng`/`weightedPick` 利用。
3. **`tileUnits(cfg,pad,cores) → Unit[]`** 【新規・主役】 — コア分断区間を `unitMix` 抽選の可変幅住戸で埋め、`buildingLengthBays` へ端数配分(justify、`parking.ts` の行 justify と同型)。各住戸へ玄関側/バルコニー側の向きを付与。
4. **`generateAptFootprint(units,cores,corridor,pad)`** — GridRect群 → `rasterizeRects`+`traceBoundary`(house/store と同一)→ ring+tier。I/L/U をバー連結。基準階を全階スタック、塔屋PH と `upperSetback` のみ tier 差。
5. **`generateAptFacade(tiers,units,cfg,lot,baseZ)`** — face role で開口切替、faceSeed で縦整列。1F/最上階/セットバック階を差し替える**例外階モデル**。
6. **`buildAptRoofs` + 塔屋** — `store/gen/roof.ts` の `buildStoreRoofs` + Canopy をそのまま。

### 8.6 テスト(`apartment.test.ts`、`store.test.ts` のヘルパ踏襲)

- **determinism**: 同一seedで2回 → JSON一致(全プリセット×複数seed)。
- **gap-free被覆**: 敷地内サンプル点の>98%がいずれかの site.zone に被覆。
- **壁長=整数ベイ**: 全 `plan.faces.length/gridModule` が整数。
- **住戸数整合**: 総戸数 == Σ(各階住戸数) == 基準階住戸数×floors(1Fテナント/ピロティ時補正)。
- **住戸幅下限**: 各間口 ≥ `unitBays[type]×gridModule`(端数吸収で潰れていない)。
- **コア到達性**: 全住戸の玄関側がコア到達廊下(階段室型は隣接コア)に接する — parking の reachability prune と同型フラッド。**到達不能住戸を出さない**(pruneで落とすと戸数整合と矛盾するため事前に必ず到達する配置を作る)。
- **コア数整合**: accessType別ルール(階段室型=`ceil(住戸数/stairSpacingUnits)`、片/中廊下=規定EV+階段、コア型=中央1)。floors≥閾値で elevator コア存在。
- **附置義務**: `parking.count >= ceil(総戸数×parkingRatio)`、駐輪同様(不足時はフラグ明示、**無音違反不可**)。
- **バルコニー面の一意性**: balcony role 面(1方向)にのみ生成、各基準階住戸に1バルコニー。
- **footprint収まり**: ring全点が敷地ring内 かつ pad クランプ内。
- **スタル敷地内**: 全スタル中心が `lot.ring` 内(角地/歪み四角でもスピルしない)。
- **塔屋/セットバックtier**: penthouse時 最上階上に外形より小さい塔屋マス、upperSetback時 上層tierが道路側後退。
- **1F差異**: pilotis/groundTenant/entrance時、1F facade が基準階と異なる panel type。

### 8.7 リスク(難所)

1. **住戸タイリングのビンパッキング** — 可変幅住戸(2〜5ベイ)+コアを `buildingLengthBays` に整数ベイで正確に詰める。端数を住戸幅拡張/廊下/端部に配分する justify(parking行同型)を入れないと隙間・住戸潰れ・非整数壁が出る。戸建 archetype 合成に無い制約。
2. **アクセス型の連鎖決定** — 片廊下=バー奥行に廊下を片面加算・バルコニー反対面、中廊下=両側振り分け+廊下内包(妻側のみ窓)、コア型=中央周回で**線形バー前提が崩れる**。footprint/facade/site が accessType で深く分岐。
3. **コア到達性の保証** — タイリング時に構造的に満たす(prune で落とさない)方が戸数整合と両立し安全。
4. **南面 vs 道路の競合** — `southFacing:'south'` だとバルコニー面が前面道路と背反し、store の「正面=道路」前提がそのまま使えない。エントランス(道路側)とバルコニー(南)の向きを独立に扱う。
5. **L字/コの字の入隅住戸** — 内側コーナーで住戸/廊下が交差、コーナー住戸の間口・採光が破綻。入隅はコア/EPS/階段に割当てるか住戸ドロップの特別処理(house の L archetype より深刻)。
6. **多層スタックの表現効率と1F差異** — 5〜22階を反復。基準階から全階 instance しつつ、1F/最上階(塔屋)/セットバック階のみ差し替える**例外階モデル**が必要(全tier個別生成は重い)。
7. **斜線セットバック** — `upperSetback` は下屋stepと逆(上が小さく道路側後退)で、footprint tier生成の一般化が要る。
8. **附置義務の物理充足** — 総戸数×parkingRatio が敷地容量を超過しがち(特に高層)。機械式/立体/隔地を持たない本プロトタイプでは不足ケースをフラグ化し、テストは「≥目標 or 明示不足」で書く。
9. **structure ゲート** — 木造は≤2〜3階・勾配・浅スパン、壁式RCは≤5階、タワーはコア型のみ。プリセット外の手動組合せ(木造20階等)で破綻しないクランプ/フォールバックが必須。

## 10. 実物写真観察に基づく立面バリエーション拡張(2026-07-05 追記)

### 10.1 背景 — 「バリエーションが効かない」問題の実物照合

M1 完成後、seed を振っても見た目が変わらないという課題が出た。コード診断では **seed がシルエット・住戸リズム・色の3チャンネルをほぼ触っておらず**(棟長=固定 `buildingLengthBays`、`tileUnits` は `evenSplit` 均等割りで rand 不使用、`accentColor`・タイル2種固定)、変化が階数と敷地内スライド・素材抽選など二次属性に偏っていた。日本の実物写真(木造2階アパート/大東建託系/レオパレス系外廊下/昭和団地/UR板状/分譲低層〜中層/ペンシル)を約20枚照合したところ、**実物で建物の個性を決めているのはまさにその3軸+バルコニー形状**であることが確認できた。以下は写真から抽出した、seed で振るべき立面バリエーション軸。

### 10.2 バルコニー形状(最大の識別要素)

現実装は「各住戸ごとの連続張出しスラブ+手摺4種」のみ。実物は**形状の型そのもの**が型式ごとに異なり、これが立面リズムを支配する。

| 型 | 実物での出現 | 立面への効き | 実装方針 |
|---|---|---|---|
| **連続スラブ** `continuous` | UR板状・レオパレス外廊下 | 水平連続のバンド。現実装 | 既存動作(各戸スラブが隣接) |
| **独立箱型** `box` | 昭和団地・古い賃貸 | 戸ごとに分離、間に外壁+小窓 →「箱・壁・箱」のリズム | 各戸スラブを縮め、左右に袖壁(返し)、戸境に外壁面を残す |
| **インセット(彫込)** `inset` | テラスハウス系2階アパート・分譲 | 建物輪郭内に食い込み、深い影の凹み。2階建てアパートはほぼ全部これ | 張出しを抑え袖壁+上げ裏で loggia 風の凹みを近似(CSG回避) |

手摺は既実装4種(glass/bars/panel/concrete)で概ね網羅。**同一建物でも面で切替わる**例(正面ガラス・妻側格子)あり。団地リノベの色付きスパンドレル(青)は `panel` の色替えで表現可。

### 10.3 窓 — 単調さの主因は「全幅1枚窓」

- **同一住戸内の非対称ミックス**: バルコニー面は「掃き出し窓+腰窓」の2種構成が多数派。現状の「住戸全幅の掃き出し窓1枚」が単調の主因。→ `windowMix: 'mixed'` で幅広住戸を sash + 腰窓に分割、位置ハッシュで左右を振る。
- **廊下面の設備感**: レオパレス系は 玄関ドア+面格子腰窓+MB+給湯器+メーターが縦に密集。MB/ドア/面格子小窓は既実装、給湯器プロップは将来。
- **妻面の3態**: 完全ブランク / 小窓列 / 縦長窓。**ブランク妻面が実物で非常に多く**、「大きな無地壁」自体が日本の集合住宅らしさ。→ `gableStyle: 'blank' | 'windows'`(現状は常に窓を置く=要ゲート)。
- **階段室の縦スリット窓**: 分譲系は階段室が別素材の縦ボリュームとして突出。既存 `coreStyle` の拡張先。

### 10.4 色・素材のツートンパターン

`accentColor` 固定・タイル2種では実物の幅を出せない。実物の主パターン:

1. **水平ツートン** `horizontal`: 濃茶タイル+白ボーダー帯(大東建託系の定番)。現実装の two-tone(1階 base)がこれの一種。切替位置は階境/腰高。
2. **縦アクセント帯** `vertical`: 戸境に木目・濃色の縦ストライプ(テラスハウス系の定番)。**現ジェネレータに無く効果大**。→ 住戸境界 u に全高の細い縦帯を別色で立てる。
3. 1F基壇・コア(階段室)のみ別素材(石貼り/煉瓦)。
4. 色相の実幅: クリーム/白/グレー/紺(ガルバ)/ブラウン/サーモンピンク。→ 壁・アクセント palette を拡張。

### 10.5 型式そのもの(M2 候補)

**テラスハウス型(縦分節)が現ジェネレータに無い**。2階建てアパート実物の主流は「各戸が1Fに玄関、戸境の縦帯で立面が縦分節」で、横積み共用廊下型とは立面文法が根本的に違う。§10.4-2 の縦帯 + `inset` バルコニーで見た目の近似は可能だが、平面レベルの縦分節(各戸専用階段)は M2 で footprint 拡張。

### 10.6 今回実装スコープ(効果順)

seed が触るチャンネルを増やす4点を M1.1 として実装:

1. `balconyForm`(continuous/inset/box)— シルエット・リズム
2. `windowMix`(single/mixed)— 開口リズム
3. `wallPattern`(horizontal/vertical/none)— 色・分節
4. `gableStyle`(blank/windows)— 妻面
5. **寸法の建物間ランダム化(シルエット+窓割リズムの主レバー)** — 「バリエーションが効かない」の真因は、seed が**棟長**と**住戸割付**を全く動かしていなかったこと(全 seed で棟長=固定 `buildingLengthBays`、`tileUnits` は evenSplit 均等割りで住戸幅も固定 → 例: midrise 全 seed で `22bay [4,4,4,4]`)。バルコニー/窓/色は表面変化で、シルエットと窓割は凍結していた。対処:
   - `buildingLengthRandom`: 棟長を `buildingLengthBays` の**等倍〜2倍**で seed 抽選(実棟長は敷地=lenCap でクランプ)。短いスタッビー棟〜長い板状まで振れる。
   - `gridModuleRandom`: **左右(街路平行=パネル幅)** を `gridModule` 中心 ±8%(実在レンジ [0.82,1.05] にクランプ)。
   - `unitDepthRandom`: **前後(奥行)** を `unitDepth` 中心 ±15%([6,13]m)。
   - `tileUnits` の**住戸間口 w を建物ごとに変える(かつ同一建物内は厳密に同幅)**: 従来は `evenSplit` で毎回同一(`[4,4,4,4]`)、後に加重パッキングを試したが「同一建物内で不均一」「過小分割(2ベイ=1.8m)」の不満が出た。最終形は **w を先に固定する**方式: `resolveUnitBays`(unitMix 加重 + seed、**下限3ベイ**でクランプ)で建物一律の間口 `w` を1回引き、`placeCores` が各セグメントを **w の倍数へ量子化**(住戸数=整数戸で表現、`bays = 戸数×w`)。よって全住戸が厳密に幅 w = **同一建物内は完全均一・過小分割なし**、seed により w=3/4/5… と建物間で窓割ピッチが変わる。棟長端数(w で割った余り)は棟をわずかに短くして吸収し、`placeCores` が返す実棟長 `totalBays`(≤ pad 幅)で footprint がバーを立てる。
   
   いずれも **整数ベイ格子は不変**(ベイ数×メートル幅=壁長)。`building.ts` が解決済み値(floors/gridModule/unitDepth/buildingLengthBays/unitBays)を `rc`・`w` に載せ、`placeCores`→`footprint(totalBays)`→`tileUnits(w)` の順で全段へ渡す。

いずれも `AptConfig` に enum/bool + seed 由来解決を追加し、既存規約(決定論・整数ベイ・単一 tunable 源)を踏襲。テスト不変条件(バルコニー数=戸数×階、隔て板数=境界×階、整数ベイ、住戸幅>=最小間口)は維持。プリセット別に既定を寄せる(木造=inset+縦帯+ブランク妻、団地系=box、中層片廊下=バルコニー auto)。

### 10.7 幅スケール 1.5倍・玄関ドアの実寸化(視認性調整)

- **横方向スケール 1.5倍**: `gridModule`(=panelW)を尺/メーターの約1.5倍(**基準1.35m**、resolveGridModule 実効レンジ [1.1,1.7])へ。住戸間口が **≈2.7〜4.5m → ≈4.0〜6.4m** に拡大し、細長い印象を解消。棟長(m)は敷地でクランプされるため、幅拡大は主に**住戸1戸の幅**に効く(bay 数は減り1戸が広くなる)。奥行は `unitDepth` にアンカーされ不変。
- **玄関ドアの実寸化**: 従来は `makeDoorModule(0.95, 階高)` で leaf≈**0.42m**(細すぎ)・開口高**2.25m**(高すぎ)だった。ドア寸法を facade が実寸で持ち(`DOOR_MODULE_W/H`)、render はドアパネルの `w/h` からモジュールを組む方式へ変更。結果 **leaf≈0.86m・開口高≈2.03m**、開口下端が床レベル(階高非依存の一定サイズ)。
- 日影測定面: その他地域は**4mまたは6.5m**(自治体選択)。
